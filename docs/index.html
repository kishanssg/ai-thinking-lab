Experiment 001 · Memory Reliability

When a fresh check
is no longer fresh.

Can current authoritative checks prevent assignments based on stale memory—even when eligibility changes between checking and writing?

Deterministic simulation. No real LLM evaluated. Our own Python/SQLite experiment uses fictional records and fixed policies. No model inference or API calls; no claim of general AI reliability.

Four workflows. One assignment rule.

The fictional worker must exist and be eligible when an assignment is written.

A · Memory only

Trusts a remembered eligibility flag and writes without checking current state.

B · Voluntary check

The simulated policy always checks, then writes unguarded. This cannot establish actual model prompt compliance.

C · Required check

An internal application wrapper requires a positive precheck. That result may become stale.

D · Atomic guard

Adds a conditional insert inside a SQLite write transaction. Eligibility is enforced at assignment time.

The time-of-check / time-of-use gap

A correct recommendation can lead to an invalid write.

  1. Check: eligible

    The authoritative lookup says yes. The recommendation is correct at this moment.

  2. State changes

    The fixture revokes eligibility after the decision and before the commit. No sleeps or timing luck.

  3. Write: enforce again

    B and C write using stale approval. D’s atomic predicate sees current ineligibility and rejects the write.

The injected race is sequential. It is not a concurrent load test, and C’s internal wrapper is not a production authorization system.

Small by design. Inspectable by default.

Six predefined scenarios: eligible and unchanged; stale true; stale false; missing worker; lookup failure; eligibility flip. Expected outcomes precede decision logic. Every run starts with a fresh in-memory database.

Python’s standard library, SQLite, deterministic traces, and eight automated tests make an application-level failure mechanism inexpensive to investigate. No external packages or paid inference are needed. This is not a cheap benchmark of actual LLM reliability.

Metrics separate incorrect affirmative recommendations, invalid commits, legitimate completion, and unnecessary refusals. Read the metric definitions.

What this does not establish

  • No actual LLM, API, or model inference was evaluated.
  • Six fictional cases cannot establish general reliability.
  • Voluntary checking is a fixed policy, not observed prompt compliance.
  • Local latency is descriptive, not a performance benchmark.
  • We did not reproduce MemRiskBench, its benchmark, or its model scores.
