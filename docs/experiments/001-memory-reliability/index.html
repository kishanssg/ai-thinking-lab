Experiment 001 · Feature

What stops a system from acting on old information?

Checking first still let a bad booking through. Checking again at the moment of saving stopped it.

By kishanssg · September 2026 · 5-minute read

At a glance

The problem
A system remembered that a worker was allowed to take a shift. That changed. The system booked the worker anyway.
What I tried
Four ways to stop that from happening, tested in 6 situations each.
What worked
Checking again at the moment of saving stopped every bad booking: 0 of 6. Checking a moment earlier still let 1 of 6 through.
The catch
No method booked more of the right workers. Each one missed 1 of 3, for different reasons.
Keep in mind
This is a small practice test on my own computer. No AI model was used, and it doesn’t prove anything about real systems.

The story

Imagine an app that books workers for shifts. Last week it noted that Sam is allowed to work a certain shift. Today Sam isn’t allowed anymore, but the app still remembers the old answer.

If the app trusts its memory, it books Sam by mistake. If it checks first, it sees the change and says no. Good.

But what if the change happens in the tiny gap after the check and before the booking is saved? The check said yes. It was right when it looked. The booking still goes through. That gap is what this experiment is about.

Why I care: AI assistants are starting to do things like this. They remember facts and then act on them. I read a research paper about AI memory going stale (MemRiskBench) and wanted to see what the software around an AI can do to catch it.

The four ways I tried

Each one adds a bit more safety than the one before
WayWhat it does
ATrust memoryUses what it remembers. Never checks.
BCheck first, by choiceLooks up the latest answer before booking. Nothing forces it to.
CCheck first, requiredSame as B, but the app refuses to book unless a check said yes.
DCheck while savingSame as C, and the save itself only works if the worker is still allowed at that moment.

Each way was tested in the same 6 situations, such as “nothing changed”, “memory is wrong” and “the answer changes right after the check”. That makes 24 tests.

The row that matters is 6. It’s the only place where “check while saving” did better than “check first”.

Why checking first wasn’t enough

Situation 6 is the one where the answer changes right after the check. Here it is as a comic strip.

For engineers: the SQL, and an honest caveat

B and C run an unguarded insert. D runs a conditional insert inside a write transaction (abridged from Store.commit):

BEGIN IMMEDIATE;
INSERT INTO assignments (shift, worker)
SELECT 'toy-shift', id FROM workers
WHERE id = 'toy-worker' AND eligible = 1;
COMMIT;

The caveat: the change in step 3 is applied before D’s transaction starts, on one in-memory connection. So BEGIN IMMEDIATE never has another writer to block, and a plain re-read right before an unguarded insert would also have scored 0/6. This test shows that checking at save time catches the change. It does not test the guard under real concurrency. BEGIN IMMEDIATE is there to make the “already booked?” check and the insert one unit against other writers.

What I learned

A check can be right and still be too early. The safest place to check is the moment you save.

Safety and usefulness are different things. Method D stopped the bad booking, but it didn’t book any more of the right workers. If I had only measured one number, I would have missed that.

Saying “no” when unsure has a cost. When the check broke (situation 5), methods B, C and D all said no, so an allowed worker was turned away. For bookings that’s probably the right call, but it’s still a cost.

What I don’t know yet

  • Is it the special save that helps, or just checking late? In this test, checking again just before saving would have worked too. To find out, I’d need two things happening at the same time, for real.
  • Would this hold on other databases? On Postgres, the same trick can still fail unless you add a lock. I haven’t tested that.
  • What if Sam stops being allowed after the booking is saved? Method D doesn’t handle that.
  • What should an AI assistant do when it gets “not allowed”? Try again, pick someone else, or ask a person?

What this test is not

  • No AI model was used. A simple fixed rule plays the part of the AI.
  • It’s small: 6 made-up situations, one worker, one shift.
  • Nothing happens at the same time. The change in situation 6 is slotted in on purpose, one step after another.
  • It’s not a copy of the MemRiskBench study and doesn’t repeat its results.

Try it yourself

You only need Python 3.13. Nothing to install. On Windows, type python instead of python3.

git clone https://github.com/kishanssg/ai-thinking-lab.git
cd ai-thinking-lab
python3 -m unittest discover -s experiments/001-memory-reliability -p "test_*.py" -v
python3 experiments/001-memory-reliability/experiment.py --output my-run.json

You’ll get the same results every time. Every number on this page is counted from the saved test records, and an automatic check makes sure the page matches them.

For engineers: how each number is counted, and all the files
  • Bad bookings (invalid commits): a booking saved while the worker wasn’t allowed at save time. Out of all 6.
  • Wrong “yes” decisions: the method decided to book when the worker wasn’t allowed at decision time. Out of all 6.
  • Right workers booked: allowed at save time, and booked. Out of the 3 situations where the worker was allowed (1, 3 and 5).
  • Right workers turned away: allowed at save time, but refused. Out of the same 3.
