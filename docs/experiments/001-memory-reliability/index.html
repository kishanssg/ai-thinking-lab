Experiment 001 · Memory reliability

When a fresh check is no longer fresh

A system that assigns work based on remembered eligibility will sometimes be wrong. Checking the database first helps, but that answer can go stale before the write happens. I built a small, deterministic Python/SQLite simulation to see which safeguards actually stop an invalid write, and what each one costs.

Findings

Deterministic simulation with synthetic data. No LLM or model API was involved. What this does not show

A · The question

Is checking first enough?

Agents and automated workflows increasingly act on things they remember: a permission, a status, a preference. Memory goes stale, and the obvious fix is to check the source of truth before acting. My question was narrower and more mechanical:

If a system checks current eligibility before writing an assignment, does that prevent invalid assignments, including when eligibility changes between the check and the write?

The idea came from reading MemRiskBench (Jiang, Yuan & Li, 2026), which evaluates LLM agents on memory risks such as acting on superseded information. I did not reproduce that benchmark. I took one failure mode it describes and asked what an application can do about it at the database layer.

B · Why it matters

A worker, a shift, and outdated eligibility

Picture a scheduling system that fills shifts. Last week it recorded that a worker was eligible for a shift. Since then, their eligibility has been revoked.

  • Assign from memory, and the worker is booked for a shift they can no longer work.
  • Check first, and the system sees the change and refuses. Good.
  • But if eligibility is revoked after the check and before the assignment is saved, the check said yes and the write goes through anyway.

That last case is a time-of-check / time-of-use (TOCTOU) race. It is easy to miss in testing because the check was correct when it ran. The experiment models the situation with one fictional worker, one shift, and a single eligible flag.

C · The experiment

Four approaches, one rule, six scenarios

Every task asks the same thing: assign toy-worker to toy-shift. The rule is that the worker must exist and have eligible = 1 when the assignment is written. Memory holds a Boolean from an earlier observation; the SQLite workers table is the source of truth. Each of the 24 runs starts from a fresh in-memory database.

The six scenarios cover the ways memory and reality can disagree: eligibility unchanged, stale “eligible”, stale “ineligible”, a worker record that no longer exists, a lookup that errors, and eligibility revoked between check and write. Expected outcomes were written into the fixtures before the runs.

How each metric is counted · denominators differ
  • Invalid commits: an assignment was written while the worker was not eligible at write time. Out of all 6 tasks.
  • Incorrect recommendations: the approach decided to assign when the worker was not eligible at decision time. Out of all 6 tasks.
  • Eligible tasks completed: the worker was eligible at write time and the assignment was written. Out of the 3 eligible tasks (unchanged, stale “ineligible”, lookup error).
  • Unnecessary refusals: the worker was eligible at write time but the approach refused. Out of the same 3 tasks.

All metrics are computed from recorded event traces, not from expected labels. Full definitions are in the methodology.

E · The interesting failure

A correct check, then an invalid write

Scenario 6, step by step. Approaches B, C and D behave identically until the moment they write.

  1. 1

    The worker is eligible

    The database record says eligible, and memory agrees.

    workers.eligible = 1
  2. 2

    The application checks

    B, C and D look up current state. The answer is yes, and it is correct at this moment.

    check → eligible
  3. 3

    Eligibility is revoked

    The fixture commits a revocation after the decision and before the write. It is injected sequentially: no threads, no sleeps, no timing luck.

    workers.eligible = 0
  4. 4

    The application tries to assign

    Each still holds the positive result from step 2, so each goes ahead and writes.

    holding: stale “yes”
  5. →

    5 · Approaches B and C

    Unguarded write

    The insert trusts the earlier check.

    INSERT INTO assignments
VALUES ('toy-shift', 'toy-worker');

    ✕ Invalid assignment committed

    6 · Approach D

    Atomic eligibility guard

    The write carries its own condition, evaluated inside the write transaction.

    BEGIN IMMEDIATE;
INSERT INTO assignments (shift, worker)
SELECT 'toy-shift', id FROM workers
WHERE id = 'toy-worker' AND eligible = 1;
COMMIT;

    ✓ 0 rows inserted, write rejected

SQL abridged from Store.commit in experiment.py. D’s predicate reads eligibility in the same statement that writes, and BEGIN IMMEDIATE takes SQLite’s write lock first, so no other writer can change the record in between.

F · What I learned

What I took away

A check is a snapshot, not a guarantee. B and C checked authoritative state on every task and still wrote one invalid assignment. Being right at decision time does not protect a later write.

Enforce the invariant where the write happens. Putting the eligibility condition into the insert, inside a write transaction, closed the gap in every tested case, and it does not depend on the caller remembering to check.

Safety and usefulness need separate metrics. With a single error rate, D would look strictly better. Measured separately, it prevented invalid writes but completed no more eligible tasks than memory-only. It failed in a different place: refusing on lookup error, where memory-only missed the stale “ineligible” task.

Failing closed is a policy choice with a cost. Refusing when the lookup errors is defensible for assignments, but here it showed up as a lost eligible task. A real system would need retries or another recovery path, which this experiment does not model.

G · Limitations

What this does not show

  • No real LLM was evaluated and no model API was called. The “agent” is a fixed Python policy.
  • Only six hand-written synthetic scenarios: one worker, one shift, one rule.
  • Checking behaviour is simulated. B always checks by construction, so it cannot show whether a model would follow a “check first” instruction.
  • The race is injected sequentially between two steps. It is not a concurrent load test.
  • C’s “required check” is an in-process wrapper, not an access-control system.
  • The results do not establish production reliability. Recorded latencies are descriptive only.
  • This is not a reproduction of MemRiskBench, its benchmark, or its model scores.

H · Reproduce

Run it yourself

Python 3.13 and nothing else: no packages, network access, or credentials. On Windows, use python instead of python3.

git clone https://github.com/kishanssg/ai-thinking-lab.git
cd ai-thinking-lab
python3 -m unittest discover -s experiments/001-memory-reliability -p "test_*.py" -v
python3 experiments/001-memory-reliability/experiment.py --output my-run.json

Logical outcomes repeat exactly; timestamps and timings vary. Using --output keeps the saved run intact. CI runs the tests and re-checks the summary counts on every push.
