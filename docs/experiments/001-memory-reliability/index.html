Experiment 001 · September 2026

Stale memory and check-then-write

An agent, or any automated workflow, that assigns work from memory will sometimes act on information that is out of date. I wanted to see what actually stops the bad write: checking first, requiring a check, or putting the condition into the write itself.

This is a small Python/SQLite simulation. No model is involved. The decisions come from a fixed policy standing in for the agent, and what I'm testing is the tool and database side.

Results in short

  • Approaches B and C checked eligibility on every task and still committed 1 of 6 invalid assignments. It came from scenario 6, where eligibility is revoked after the check and before the write.
  • Approach D puts the eligibility condition in the INSERT and committed 0 of 6. A plain re-read just before the write would have scored the same in this setup; scenario 6 explains why.
  • Every approach completed 2 of 3 eligible tasks. That depends heavily on which scenarios I picked: each approach lost exactly one, for a different reason.

The metrics are counted from recorded event traces rather than expected labels, and CI checks that the numbers on this page match the saved results.

The question

I was reading MemRiskBench (Jiang, Yuan & Li, 2026), which tests LLM agents on memory problems, including acting on information that has since been updated. I did not reproduce that benchmark. I took one failure mode it describes and asked what the application can do about it at the database layer.

If a system checks eligibility right before it writes an assignment, is that enough? And what happens if eligibility changes between the check and the write?

In an agent, the “policy” would be the model deciding whether to call a tool, and the guard would live inside the tool. I only built the tool side.

The example

A scheduling system remembers that a worker is eligible for a shift, but the worker’s eligibility has since been revoked. If it assigns from memory, the worker ends up on a shift they can’t work. If it checks first, it sees the change and refuses.

The harder case is a revocation that lands after the check but before the assignment is saved. The check was correct when it ran, so this is easy to miss in tests. It’s the classic time-of-check / time-of-use problem.

The simulation uses one fictional worker, one shift and a single eligible flag.

Setup

Every task does the same thing: assign toy-worker to toy-shift. The worker has to exist and have eligible = 1 when the assignment is written. Memory is a Boolean from an earlier observation, and the SQLite workers table is the source of truth. Each of the 24 runs gets a fresh in-memory database.

The six scenarios: eligibility unchanged, memory says eligible but the worker isn’t, memory says ineligible but the worker is, the worker record is gone, the lookup errors, and eligibility is revoked between check and write. Each fixture also lists its expected outcome, and the tests check all 24.

How each metric is counted (the denominators differ)
  • Invalid commits: an assignment was written while the worker was not eligible at write time. Out of all 6 tasks.
  • Incorrect recommendations: the approach decided to assign when the worker was not eligible at decision time. Out of all 6 tasks.
  • Eligible tasks completed: the worker was eligible at write time and the assignment was written. Out of the 3 eligible tasks (unchanged, stale “ineligible”, lookup error).
  • Unnecessary refusals: the worker was eligible at write time but the approach refused. Out of the same 3 tasks.

Scenario 6, step by step

B, C and D behave identically until the write.

  1. 1

    The worker is eligible

    The database record says eligible, and memory agrees.

    workers.eligible = 1
  2. 2

    The application checks

    B, C and D look up current state. It says yes, which is true right then.

    check → eligible
  3. 3

    Eligibility is revoked

    The fixture revokes eligibility after the decision and before the write. It runs sequentially, in the same process.

    workers.eligible = 0
  4. 4

    The application tries to assign

    Each still holds the positive result from step 2, so each goes ahead and writes.

    holding: stale “yes”
  5. →

    5 · Approaches B and C

    Unguarded write

    The insert trusts the earlier check.

    INSERT INTO assignments
VALUES ('toy-shift', 'toy-worker');

    ✕ Invalid assignment committed

    6 · Approach D

    Guarded insert

    The insert checks eligibility itself, inside the transaction.

    BEGIN IMMEDIATE;
INSERT INTO assignments (shift, worker)
SELECT 'toy-shift', id FROM workers
WHERE id = 'toy-worker' AND eligible = 1;
COMMIT;

    ✓ 0 rows inserted, returns ineligible_or_missing

SQL abridged from Store.commit in experiment.py. D’s eligibility condition is part of a single INSERT … SELECT; BEGIN IMMEDIATE makes the already-assigned check and the insert one unit against other writers. One caveat: the revocation happens before D’s transaction starts, on a single in-memory connection, so BEGIN IMMEDIATE never has another writer to block. This scenario shows that checking at write time catches the change. It does not test the guard against concurrent writers.

What I took from it

The check in B and C was right when it ran. By the time the write happened, it wasn’t. Putting the condition in the INSERT fixed that case, and it doesn’t depend on the caller remembering to check.

I nearly reported a single error rate. With one number, D would have looked strictly better than everything else. Counting invalid writes and completed tasks separately shows it blocked one more bad write and finished no more real tasks, though with these fixtures each of those comes down to a single scenario.

D refuses when the lookup errors. For assignments that’s probably the right default, but here it cost an eligible task.

Open questions

  • Does the guard matter, or just checking late? Because the revocation is applied before the write starts, re-reading eligibility right before an unguarded insert would also score 0/6 here. To tell them apart I’d need real concurrency, meaning a file-backed database with two connections and a revocation that lands between the re-read and the insert.
  • Other databases. On Postgres at READ COMMITTED, INSERT … SELECT … WHERE eligible = 1 can still race a concurrent update. It would need a row lock (FOR SHARE), SERIALIZABLE isolation, or a trigger. I haven’t tested that.
  • D only checks at insert time. If eligibility is revoked after the assignment is saved, the assignment stays. The revoke path would have to deal with existing assignments.
  • In an agent, a rejected write should come back as a structured error the agent can act on: retry the lookup, re-plan, or ask a person. The lookup-failure scenario is where that choice matters.

Limitations

  • No LLM or model API was used. The “agent” is a fixed Python policy, so approach B can’t show whether a model would follow a check-first instruction.
  • Six hand-written scenarios with one worker, one shift and one rule.
  • The revocation is applied sequentially on one in-memory connection. Nothing runs concurrently.
  • C’s required check is an in-process wrapper, not access control.
  • This is not a reproduction of MemRiskBench or its results.
