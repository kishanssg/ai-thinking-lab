Experiment 001 · Feature

Checking first wasn’t enough

A manager cancelled a store credit just after an AI support agent checked it. The agent added the credit anyway. Checking first wasn’t enough; the check and the action had to be one locked step.

By kishanssg · September 2026 · 5-minute read

For engineers: a time-of-check / time-of-use (TOCTOU) bug in a simulated agent tool call, fixed by doing the check and the write in one locked transaction. Python + SQLite; 24 recorded runs, plus a Part 2 stress test with 9,000 tries per method.

At a glance

The problem
An AI support agent remembered that a customer was approved for a $20 store credit. A manager cancelled the approval just after the agent checked. The agent added the credit anyway.
What I tried
Four ways to stop that, each tested in the same 6 situations.
What worked
In the one situation built to test this timing, checking first let the wrong credit through. Doing the check inside the step that adds the credit stopped it.
Part 2
A stress test with the cancellation landing within a few milliseconds: a separate re-check just before adding the credit still let it through in about 1 of 6 tries. A locked check-and-add step let none through.
The catch
No method gave more of the credits customers were really owed. Trust memory refused one because its memory was wrong; the three checking methods each refused one because the check broke.
Keep in mind
I tested the safety net around an AI agent, not the AI itself. A simple rule plays the agent, and the whole test is small.

The story

Imagine an AI agent that helps with customer support. Earlier today a $20 goodwill credit was approved for customer #42, and the agent remembers that.

Then the customer withdraws the complaint and a manager cancels the credit. If the agent trusts its memory, it adds a credit the customer is no longer owed. If it checks the customer’s record first, it sees the cancellation and says no. Good.

But what if the manager cancels it in the tiny gap after the agent checks the record and before it adds the credit? The check said yes, and it was right when it looked. The credit still goes on. That gap is what this experiment is about.

Why store credit and not a refund? Payment providers won’t refund more than was paid, and many let you tag a request so it can’t be processed twice. Internal tools, like adding store credit, often have no such protection. That’s where an AI agent with a tool can slip.

Why I care: AI agents are starting to remember things and then act with real tools, like issuing credits. I read MemRiskBench, a research paper about the ways AI memory goes wrong, including using something after it was taken back. The paper doesn’t test this timing gap. That part is my own small extension.

The four ways I tried

Each one adds a bit more safety than the one before

Why checking first wasn’t enough

Situation 6, as a comic strip.

For engineers: the SQL, and an honest caveat

B and C run an unguarded insert. D runs a conditional insert inside a write transaction (abridged from Store.commit):

BEGIN IMMEDIATE;
INSERT INTO credits (credit_id, customer)
SELECT 'credit-42', id FROM customers
WHERE id = 'customer-42' AND approved = 1;
COMMIT;

The caveat: the change in step 2 is applied before D’s transaction starts, on one in-memory connection. So BEGIN IMMEDIATE never has another writer to block, and a plain re-read right before an unguarded insert would also have scored 0/6. This test shows that checking at write time catches the change. It does not test the guard under real concurrency; Part 2 does. BEGIN IMMEDIATE is there to make the “already done?” check and the insert one unit against other writers.

Part 2: a real stress test

The test above couldn’t tell whether the special guarded step mattered, or whether any late re-check would do. So I ran a tougher version as Part 2 of this experiment. This time the manager’s cancellation really raced the agent, landing within a few milliseconds of it, 3,000 times per method, three runs.

Wrong credits when the cancellation really races the agent
MethodWrong creditsWhat it does
Check first, required2,617 of 9,000 (29%)The same as method C above.
Re-check just before giving1,611 of 9,000 (18%)Looks again right before giving the credit, as a separate step.
Check and give as one locked step0 of 9,000Re-check and add the credit inside one write transaction that locks out other changes.
Check while giving (method D)0 of 9,000The guarded step from above, inside a transaction.

A quick re-check isn’t enough. What works is making the check and the action one locked step, so nothing can change in between. In SQLite, a write transaction does that because it locks out other writers. Postgres would need an explicit row lock. The special guarded step wasn’t the important part.

These rates come from one laptop and change from run to run. Zero is what the database’s locking should guarantee, but it’s still an observation, not a proof. Only SQLite was tested. Code, method and full results.

What I learned

A check can be right and still be too early. Even a re-check right before acting wasn’t enough once things really happened at the same time. The check and the action need to be one locked step.

Safety and usefulness are different things. Method D stopped the wrong credit, but it didn’t give any more of the credits customers were really owed. If I had only measured one number, I would have missed that.

Saying “no” when unsure has a cost. When the check broke (situation 5), methods B, C and D all said no, so a customer who was owed a credit didn’t get it. For money that’s probably the right call, but it’s still a cost.

What I don’t know yet

  • Would this hold on other databases? On Postgres, the same trick can still fail unless you add a lock. I haven’t tested that.
  • What if the record changes after the credit is added? Method D doesn’t handle that.
  • What should the agent do when it hears “cancelled”? Tell the customer, check again later, or ask a person?
  • What would a real AI model do in the agent’s place? That’s a good next experiment.

What this test is not

  • No AI model was used. A simple fixed rule plays the part of the agent.
  • It’s small: 6 made-up situations and one yes/no rule.
  • In this test nothing happens at the same time; the change in situation 6 is slotted in on purpose. Part 2 covers real timing, on one laptop and SQLite only.
  • The paper doesn’t test this timing gap. This is my own extension, not a copy of the MemRiskBench study.

Try it yourself

You only need Python 3.13. Nothing to install. On Windows, type python instead of python3.

git clone https://github.com/kishanssg/ai-thinking-lab.git
cd ai-thinking-lab
python3 -m unittest discover -s experiments/001-memory-reliability -p "test_*.py" -v
python3 experiments/001-memory-reliability/experiment.py --output my-run.json

You’ll get the same results every time. Every number on this page is counted from the saved test records, and an automatic check makes sure the page matches them.

For engineers: how each number is counted, and all the files
  • Wrong credits (invalid commits): an action saved when it wasn’t allowed at that moment. Out of all 6.
  • Wrong “yes” decisions: the method decided to act when it wasn’t allowed at decision time. Out of all 6.
  • Fair credits given: allowed at save time, and done. Out of the 3 situations where it was allowed (1, 3 and 5).
  • Fair credits refused: allowed at save time, but refused. Out of the same 3.
