Experiment 001 · Feature

Checking first wasn’t enough

In a small test, an AI refund agent’s safety check still let a double refund through. Checking again at the moment of refunding stopped it.

By kishanssg · September 2026 · 5-minute read

For engineers: a time-of-check / time-of-use (TOCTOU) bug in a simulated agent tool call, fixed with a guarded write. Python + SQLite, 24 recorded runs.

At a glance

The problem
An AI agent that handles refunds remembered that an order could be refunded. Someone else refunded it first. The agent refunded it again.
What I tried
Four ways to stop that, each tested in the same 6 situations.
What worked
Doing the check inside the refund step stopped every wrong refund: 0 of 6. Checking a moment earlier still let 1 of 6 through.
Follow-up
A tougher stress test showed a quick re-check just before refunding still fails about 1 time in 6. The check and the refund must be one locked step.
The catch
No method gave more of the fair refunds. Each one refused a fair refund once, for different reasons.
Keep in mind
I tested the safety net around an AI agent, not the AI itself. A simple rule plays the agent, and the whole test is small.

The story

Imagine an AI agent that handles refunds for an online shop. Earlier today it learned that order #42 can be refunded, and it remembers that.

If the agent trusts its memory, it might refund an order that was already refunded. If it checks first, it sees the change and says no. Good.

But what if a teammate refunds the order in the tiny gap after the agent checks and before it sends the money? The check said yes, and it was right when it looked. The refund still goes out, and the shop pays twice. That gap is what this experiment is about.

Why I care: AI agents are starting to remember things and then act with real tools, like sending money. I read MemRiskBench, a research paper about the ways AI memory goes wrong, including using something after it was taken back. The paper doesn’t test this timing gap. That part is my own small extension.

One honesty note: the test code uses a plain yes/no “allowed” flag (it calls it a worker and a shift). The refund story is an everyday picture of that same check.

Each one adds a bit more safety than the one before

Why checking first wasn’t enough

Situation 6, as a comic strip.

For engineers: the SQL, and an honest caveat

B and C run an unguarded insert. D runs a conditional insert inside a write transaction (abridged from Store.commit):

BEGIN IMMEDIATE;
INSERT INTO assignments (shift, worker)
SELECT 'toy-shift', id FROM workers
WHERE id = 'toy-worker' AND eligible = 1;
COMMIT;

The caveat: the change in step 2 is applied before D’s transaction starts, on one in-memory connection. So BEGIN IMMEDIATE never has another writer to block, and a plain re-read right before an unguarded insert would also have scored 0/6. This test shows that checking at write time catches the change. It does not test the guard under real concurrency; the follow-up does. BEGIN IMMEDIATE is there to make the “already done?” check and the insert one unit against other writers.

Follow-up: a real stress test

The test above couldn’t tell whether the special refund step mattered, or whether any late re-check would do. So I ran a tougher version (Experiment 001b). This time the teammate’s change really happened at the same moment as the agent’s refund, 3,000 times per method, three runs.

Wrong refunds when things really happen at the same time
MethodWrong refundsWhat it does
Check first, required2,460 of 9,000 (27%)The same as method C above.
Re-check just before refunding1,472 of 9,000 (16%)Looks again right before refunding, as a separate step.
Check and refund as one locked step0 of 9,000Re-check and refund inside one database transaction.
Check while refunding (method D)0 of 9,000The guarded refund from above, inside a transaction.

A quick re-check isn’t enough. What works is making the check and the refund one locked step, so nothing can change in between. In SQLite that means a write transaction. The special guarded refund wasn’t the important part.

These rates come from one laptop and change from run to run. Zero is what the database’s locking should guarantee, but it’s still an observation, not a proof. Only SQLite was tested. Code, method and full results.

What I learned

A check can be right and still be too early. Even a re-check right before acting wasn’t enough once things really happened at the same time. The check and the action need to be one locked step.

Safety and usefulness are different things. Method D stopped the wrong refund, but it didn’t give any more of the fair refunds. If I had only measured one number, I would have missed that.

Saying “no” when unsure has a cost. When the check broke (situation 5), methods B, C and D all said no, so a customer who deserved a refund didn’t get one. For money that’s probably the right call, but it’s still a cost.

What I don’t know yet

  • Would this hold on other databases? On Postgres, the same trick can still fail unless you add a lock. I haven’t tested that.
  • What if the order changes after the refund is sent? Method D doesn’t handle that.
  • What should the agent do when it hears “already refunded”? Tell the customer, check again later, or ask a person?
  • What would a real AI model do in the agent’s place? That’s a good next experiment.

What this test is not

  • No AI model was used. A simple fixed rule plays the part of the agent.
  • It’s small: 6 made-up situations and one yes/no rule.
  • In this test nothing happens at the same time; the change in situation 6 is slotted in on purpose. The follow-up covers real timing, on one laptop and SQLite only.
  • The paper doesn’t test this timing gap. This is my own extension, not a copy of the MemRiskBench study.

Try it yourself

You only need Python 3.13. Nothing to install. On Windows, type python instead of python3.

git clone https://github.com/kishanssg/ai-thinking-lab.git
cd ai-thinking-lab
python3 -m unittest discover -s experiments/001-memory-reliability -p "test_*.py" -v
python3 experiments/001-memory-reliability/experiment.py --output my-run.json

You’ll get the same results every time. Every number on this page is counted from the saved test records, and an automatic check makes sure the page matches them.

For engineers: how each number is counted, and all the files
  • Wrong refunds (invalid commits): an action saved when it wasn’t allowed at that moment. Out of all 6.
  • Wrong “yes” decisions: the method decided to act when it wasn’t allowed at decision time. Out of all 6.
  • Fair refunds given: allowed at save time, and done. Out of the 3 situations where it was allowed (1, 3 and 5).
  • Fair refunds refused: allowed at save time, but refused. Out of the same 3.
